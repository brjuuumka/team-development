# Спецификация требований к системе медицинских рецептов

В документе перечислены базовые требования к ядру и требования третьего спринта. Бизнес-правила BR-01–BR-07 остаются бэклогом будущего API и не входят в объём спринта 3.

## 1. Бизнес-правила (бэклог будущего API)

| ID | Требование | Критерий приёмки |
|---|---|---|
| BR-01 | Уникальность выписки | Для рецепта допускается ровно одно событие `ISSUED`; повтор отклоняется. |
| BR-02 | Статус для погашения | Погашается только активный непросроченный рецепт. |
| BR-03 | Однократное погашение | Рецепт погашается целиком один раз. |
| BR-04 | Права на отмену | Отменить активный рецепт может только выписавший врач. |
| BR-05 | Неизменяемость истории | Отмена добавляется новым событием и не удаляет выписку. |
| BR-06 | Доступ к данным | Подробности доступны с учётом роли пользователя. |
| BR-07 | Валидность документа | Документ с содержимым, отличным от сохранённого хэша, отклоняется. |

## 2. Базовые требования к ядру

| ID | Требование | Критерий приёмки |
|---|---|---|
| CORE-01 | Создание и проверка `Record` | Обязательные поля, UUID, тип события и хэши валидируются. |
| CORE-02 | Детерминированное хеширование | RFC 8785 и SHA-256 дают одинаковый результат при любом порядке ключей JSON. |
| CORE-03 | Genesis-блок | Первый блок имеет индекс 0, пустой список записей и `previous_hash`, состоящий из 64 нулей. |
| CORE-04 | Добавление блока | Индекс увеличивается на 1, а `previous_hash` равен хэшу предыдущего блока. |
| CORE-05 | Проверка цепочки | Проверяются структура, записи, индексы, хэши, genesis и связи блоков. |
| CORE-06 | Защита от дубликатов | Повтор `record_id` отклоняется без изменения цепочки. |
| CORE-07 | Чтение истории | События рецепта возвращаются в хронологическом порядке. |
| CORE-08 | Экспорт и импорт | JSON импортируется целиком только после успешной проверки; ошибка не меняет текущую цепочку. |
| CORE-09 | Изоляция объектов | Изменение переданных вызывающим кодом объектов не меняет сохранённую цепочку. |
| CORE-10 | Атомарность | Ошибка любой записи при добавлении не изменяет цепочку. |

## 3. Требования третьего спринта

### CORE-11 — Проверка хэша каждой записи

Формат записи версии 2 содержит поле `record_hash`. Оно равно SHA-256 от канонического JSON RFC 8785 всех полей записи, кроме самого `record_hash`. `document_hash` — отдельный хэш содержимого внешнего документа и не заменяет `record_hash`.

**Критерии приёмки:**

- При создании записи `record_hash` вычисляется автоматически.
- При импорте значение `record_hash` читается из файла, а не пересоздаётся из импортированного содержимого.
- `validate_chain()` сравнивает сохранённый `record_hash` с пересчитанным для каждой записи.
- Изменение поля записи обнаруживается даже если после изменения пересчитать хэш содержащего её блока.

### CORE-12 — Проверка цепочки и локализация ошибки

`Blockchain.validate_chain()` возвращает словарь результата и не выбрасывает исключение на обнаруженном повреждении:

- успех: `{"valid": true, "error_block_index": null, "error_record_id": null, "reason": null}`;
- ошибка: `valid=false`, индекс первого повреждённого блока, `error_record_id` для ошибки записи (иначе `null`) и `reason` с машинным кодом и пояснением.

Проверки выполняются от genesis к последнему блоку. Валидатор проверяет genesis-инварианты, версию и индекс блока, уникальность ID записей, формат и хэш каждой записи, связь с предыдущим блоком, затем хэш блока. Коды включают `INVALID_GENESIS`, `INDEX_MISMATCH`, `INVALID_RECORD_FIELD`, `RECORD_HASH_MISMATCH`, `PREVIOUS_HASH_MISMATCH`, `HASH_MISMATCH` и `DUPLICATE_RECORD`.

**Критерий приёмки:** для каждой ошибки указывается точный индекс блока; для повреждённой записи также возвращается её ID; валидная цепочка даёт `valid=true`.

### CORE-13 — Проверка внешнего JSON-файла

`Blockchain.verify_external_document(document_path, record_id)` читает JSON-файл в UTF-8, разбирает объект, канонизирует его по RFC 8785, вычисляет SHA-256 и сравнивает с `document_hash` найденной записи. Метод возвращает `True` при совпадении и `False` при неизвестном ID, отсутствии файла, неверном JSON, JSON-значении не-объектного типа или несовпадении хэша.

**Критерий приёмки:** исходный пример документа проходит проверку; изменение любого значения, включая добавление или удаление поля, даёт `False`; изменение только порядка ключей не меняет результат.

## 4. Формат данных и совместимость

В версии 2 добавляется `record_hash`; версии 1 импортировать нельзя, так как они не содержат контрольного хэша записи. Импорт неизвестной/старой версии завершается `ValueError` и оставляет текущую цепочку без изменений. Пример обновлён в `examples/valid-chain.json`. Пример документа остаётся отдельным JSON версии 1: его `schema_version` относится к формату самого документа.

## 5. Ограничение модели угроз

Хэширование обеспечивает обнаружение изменения записи при сохранении её первоначального `record_hash`, а цепочка — нарушения связей блоков. Локальная цепочка без цифровой подписи или внешней доверенной контрольной точки не доказывает автора и не обнаруживает согласованную замену последнего блока вместе со всеми его хэшами. Для защиты от такого переписывания нужен отдельный механизм подписи/внешней фиксации головы цепочки; он не входит в этот спринт.
