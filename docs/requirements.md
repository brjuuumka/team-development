# Спецификация требований к системе медицинских рецептов

В данном документе собраны все утвержденные бизнес-правила и технические требования к ядру блокчейна, разработанные в ходе Спринтов 1–3.

## 1. Бизнес-правила (Бэклог для будущего API)

Эти правила описывают логику предметной области (медицинские рецепты):

| ID | Требование | Критерий приёмки |
|---|---|---|
| BR-01 | Уникальность выписки | Для рецепта допускается ровно одно событие `ISSUED`. Повторная выписка отклоняется. |
| BR-02 | Статус для погашения | Погашается только активный непросроченный рецепт. Отменённые или просроченные отклоняются. |
| BR-03 | Однократное погашение | Рецепт погашается (`DISPENSED`) целиком один раз. Конкурирующие запросы разрешаются в пользу первого. |
| BR-04 | Права на отмену | Отмена (`CANCELLED`) доступна только выписавшему врачу для активного рецепта. |
| BR-05 | Неизменяемость истории | Отмена не удаляет исходное событие выписки, а добавляется новым блоком в цепочку. |
| BR-06 | Доступ к данным | Подробности рецепта возвращаются строго с учетом роли (пациент видит только свои). |
| BR-07 | Валидность документа | Изменённый внешний документ определяется ядром как несоответствующий хэшу и отклоняется. |

## 2. Базовые функциональные требования к ядру (CORE)

Эти требования описывают правила работы самой цепочки блоков на базовом уровне:

| ID | Требование | Критерий приёмки |
|---|---|---|
| CORE-01 | Создание и проверка `Record` | Обязательные поля, форматы (UUID) и тип события строго проверяются при инициализации. |
| CORE-02 | Детерминированное хеширование | Канонизация JSON (RFC 8785) гарантирует одинаковый SHA-256 хэш независимо от исходного порядка ключей. |
| CORE-03 | Фиксированный genesis-блок | Цепочка всегда стартует с блока с индексом 0, пустыми записями и нулевым `previous_hash`. |
| CORE-04 | Добавление блока | Индекс нового блока равен +1 от предыдущего; `previous_hash` равен хэшу прошлого блока. |
| CORE-05 | Проверка цепочки | Система умеет пересчитывать индексы, поля, хэши и связи блоков для проверки целостности. |
| CORE-06 | Защита от дубликатов | Повтор `record_id` внутри текущего блока или в истории отклоняется без изменения базы. |
| CORE-07 | Чтение истории | Метод возвращает все события по `prescription_id` в хронологическом порядке. |
| CORE-08 | Экспорт и импорт | Цепочка выгружается/загружается в формате JSON. Импорт битого файла отменяется целиком. |
| CORE-09 | Неизменяемость объектов | Изменение исходного списка данных в памяти после передачи в ядро не меняет данные внутри сформированного блока. |
| CORE-10 | Атомарность | Ошибка валидации хотя бы одной записи при добавлении оставляет цепочку в изначальном состоянии. |

## 3. Требования к глубокой защите и валидации (Спринт 3)

Эти требования обеспечивают криптографическую «честность» цепочки и защиту от подделок:

| ID | Требование | Критерий приёмки |
|---|---|---|
| CORE-11 | Детализированная валидация | Метод валидации пересчитывает хэши на уровне *каждой записи* внутри блока. Любая скрытая модификация фиксируется как ошибка. |
| CORE-12 | Локализация точки разрыва | При несовпадении хэшей метод не падает, а возвращает точный индекс поврежденного блока и текстовое описание причины (например, `PREVIOUS_HASH_MISMATCH`). |
| CORE-13 | Проверка внешнего документа | Метод `verify_external_document` канонизирует переданный внешний JSON-файл, вычисляет его SHA-256 и сверяет с `document_hash` внутри цепочки. Возвращает статус совпадения. |
