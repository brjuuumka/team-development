# Контракт взаимодействия узлов — спринт 4

**Проект:** Реестр медицинских рецептов на лекарства  
**Версия документа:** 1.0  
**Формат обмена:** HTTP + JSON  
**Кодировка:** UTF-8  
**Версия схемы блокчейна:** 2

## 1. Назначение

Документ определяет требования и контракт взаимодействия независимых узлов блокчейн-сети.

Каждый узел представляет собой отдельный экземпляр программы с собственным идентификатором и локальным хранилищем цепочки.

В рамках четвёртого спринта необходимо обеспечить:
- получение информации о другом узле;
- получение блока по его индексу;
- передачу блока другому узлу;
- проверку полученного блока перед сохранением;
- отклонение некорректных блоков;
- сохранение цепочки после перезапуска узла.

Автоматическая синхронизация и консенсус между узлами не входят в текущий объём работ.

## 2. Общие правила взаимодействия

1. Обмен данными осуществляется посредством HTTP.
2. Тела запросов и ответов передаются в формате JSON.
3. Кодировка данных — UTF-8.
4. Каждый узел имеет собственный `node_id` и отдельный файл хранения.
5. Все узлы используют совместимую схему блокчейна версии 2.
6. Полученный блок проверяется до добавления в локальную цепочку.
7. При ошибке проверки цепочка и файл хранилища не должны изменяться.
8. Передача блока не означает автоматическую синхронизацию всей цепочки.

## 3. Контракт блока

Передаваемый блок должен содержать следующие поля:

| Поле | Тип | Описание |
|---|---|---|
| schema_version | integer | Версия схемы |
| index | integer | Индекс блока |
| timestamp | string | Время создания |
| previous_hash | string | Хэш предыдущего блока |
| records | array | Массив записей |
| hash | string | Хэш текущего блока |

Каждая запись должна содержать:

| Поле | Тип | Описание |
|---|---|---|
| schema_version | integer | Версия схемы |
| record_id | string | Уникальный идентификатор записи |
| prescription_id | string | Идентификатор рецепта |
| event_type | string | Тип события |
| actor_id | string | Идентификатор участника |
| created_at | string | Время создания записи |
| document_ref | string | Ссылка-идентификатор документа |
| document_hash | string | Хэш документа |
| record_hash | string | Хэш содержимого записи |

В передаваемых объектах должны присутствовать все обязательные поля. Лишние поля не допускаются.

## 4. HTTP API

### 4.1. Получение информации об узле

**Метод:** GET  
**Адрес:** `/v1/node`

Назначение: получение идентификатора узла и состояния его блокчейна.

Успешный ответ: HTTP 200.

Пример:

```json
{
  "node_id": "node-a",
  "schema_version": 2,
  "height": 1,
  "last_hash": "64-символьный-хэш",
  "valid": true
}
```

Поля ответа:
- `node_id` — идентификатор узла;
- `schema_version` — версия формата;
- `height` — индекс последнего блока;
- `last_hash` — хэш последнего блока;
- `valid` — результат проверки цепочки.

### 4.2. Получение блока

**Метод:** GET  
**Адрес:** `/v1/blocks/{index}`

Назначение: запрос блока по индексу у известного узла.

Пример запроса:

`GET /v1/blocks/1`

Успешный ответ: HTTP 200.

```json
{
  "block": {
    "schema_version": 2,
    "index": 1,
    "timestamp": "2026-09-24T09:00:00.000Z",
    "previous_hash": "64-символьный-хэш",
    "records": [],
    "hash": "64-символьный-хэш"
  }
}
```

Если блока с указанным индексом нет, возвращается HTTP 404 с описанием `BLOCK_NOT_FOUND`.

### 4.3. Передача блока другому узлу

**Метод:** POST  
**Адрес:** `/v1/blocks`

Назначение: передача блока принимающему узлу.

Тело запроса содержит JSON-объект блока согласно контракту раздела 3.

Успешный ответ: HTTP 201.

```json
{
  "accepted": true,
  "block": {
    "schema_version": 2,
    "index": 1,
    "timestamp": "2026-09-24T09:00:00.000Z",
    "previous_hash": "64-символьный-хэш",
    "records": [],
    "hash": "64-символьный-хэш"
  }
}
```

Принимающий узел обязан проверить:
1. Поддерживаемую версию схемы.
2. Наличие обязательных полей и отсутствие лишних.
3. Корректность каждой записи.
4. Соответствие хэшей записей.
5. Соответствие хэша блока его содержимому.
6. Правильность индекса нового блока.
7. Соответствие `previous_hash` хэшу последнего локального блока.
8. Отсутствие повторяющихся `record_id`.
9. Наличие хотя бы одной записи в новом блоке.

Блок сохраняется только после успешного прохождения всех проверок.

### 4.4. Создание демонстрационного блока

**Метод:** POST  
**Адрес:** `/v1/blocks/create`

Назначение: создание тестового блока на текущем узле для демонстрации работы системы.

Тело запроса — JSON-объект с необязательными параметрами тестовой записи.

Успешный ответ: HTTP 201.

```json
{
  "block": {
    "index": 1,
    "timestamp": "2026-09-24T09:00:00.000Z",
    "previous_hash": "64-символьный-хэш",
    "records": [],
    "hash": "64-символьный-хэш"
  }
}
```

Данный маршрут предназначен для демонстрационного сценария.

## 5. Контракт ошибок

При отклонении блока сервер возвращает HTTP 422.

Общий формат ответа:

```json
{
  "accepted": false,
  "error": "ERROR_CODE: описание ошибки"
}
```

Поддерживаемые ошибки:

| Код | Причина |
|---|---|
| INVALID_REQUEST | Некорректное тело запроса |
| INVALID_RECORD | Некорректная запись |
| INVALID_BLOCK | Некорректный блок |
| UNSUPPORTED_SCHEMA_VERSION | Неподдерживаемая версия схемы |
| HASH_MISMATCH | Хэш блока не соответствует содержимому |
| RECORD_HASH_MISMATCH | Хэш записи не соответствует содержимому |
| PREVIOUS_HASH_MISMATCH | Нарушена связь с предыдущим блоком |
| INDEX_MISMATCH | Неправильный индекс или пропущен блок |
| DUPLICATE_RECORD | Повторяется идентификатор записи |
| DUPLICATE_BLOCK | Блок уже присутствует в цепочке |
| CHAIN_CONFLICT | На данной высоте уже существует другой блок |
| EMPTY_BLOCK | Блок не содержит записей |
| ROUTE_NOT_FOUND | Запрошенный маршрут не существует |
| BLOCK_NOT_FOUND | Блок с таким индексом отсутствует |

Неизвестный маршрут возвращает HTTP 404.

При ошибке приёма блока локальная цепочка и файл хранения остаются без изменений.

## 6. Сценарии взаимодействия

### Сценарий 1. Получение информации об узле

1. Узел A отправляет GET-запрос узлу B.
2. Узел B формирует информацию о своём состоянии.
3. Узел A получает JSON-ответ.
4. Информация может использоваться для отображения состояния удалённого узла.

### Сценарий 2. Передача нового блока

1. На узле A создаётся новый блок.
2. Узел A получает его данные.
3. Блок отправляется на адрес узла B методом POST.
4. Узел B проверяет полученные данные.
5. При успешной проверке блок добавляется в локальную цепочку.
6. Узел B сохраняет обновлённую цепочку.

### Сценарий 3. Получение блока по запросу

1. Узел B отправляет GET-запрос узлу A с индексом нужного блока.
2. Узел A возвращает блок.
3. Узел B проверяет полученный блок.
4. При успешной проверке блок сохраняется локально.

### Сценарий 4. Отклонение некорректного блока

1. Узел A отправляет изменённый или некорректный блок.
2. Узел B выполняет проверку.
3. При обнаружении ошибки возвращается соответствующий код.
4. Цепочка узла B остаётся без изменений.

## 7. Ограничения

В рамках четвёртого спринта не реализуются:
- автоматическое обнаружение узлов;
- автоматическая синхронизация цепочек;
- алгоритм консенсуса;
- автоматическое разрешение конфликтов;
- аутентификация и цифровые подписи узлов;
- шифрование соединения посредством TLS.

Текущая реализация предназначена для локальной учебной демонстрации и не должна использоваться с реальными медицинскими данными или в открытой сети.

## 8. Критерии приёмки

Работа считается соответствующей требованиям, если:
- можно запустить минимум два независимых узла;
- каждый узел использует собственное хранилище;
- можно получить информацию о другом узле;
- можно запросить блок по индексу;
- можно передать блок другому узлу;
- принимающий узел проверяет блок перед сохранением;
- некорректный блок отклоняется с описанием ошибки;
- после отклонения состояние цепочки не меняется;
- после перезапуска данные восстанавливаются из локального хранилища.
